# Бэкенд «100 деңгей» — схема и перенос контента

Это понедельник и вторник из плана недели 18–24 августа, написанные заранее.
Учётные данные не нужны: SQL готов, остаётся выполнить его в Supabase.

## Зачем

Сегодня все 240 вопросов **вместе с индексом верного ответа** лежат в исходнике
страницы, а прогресс подставляется параметром `?done=` в адресной строке.
Пока это так, «100 деңгей» нельзя дать чужому ребёнку по ссылке — а значит,
фича не сделана, как бы хорошо она ни выглядела.

## Главное решение

**Индекс верного ответа никогда не уходит клиенту.** Клиент получает вопрос
и четыре варианта, отправляет свой выбор, сервер возвращает
`{верно, верный индекс, объяснение}` — и только для того вопроса, на который
ребёнок уже ответил. Скачать весь банк невозможно.

Технически это три вещи в `schema.sql`:

1. У таблицы `sl_questions` **нет ни одной политики на `select`**.
   Значит читать её напрямую не может никто, кроме `service_role`.
   Это не забытая строка — это и есть защита, туда нельзя дописывать политику.
2. Наружу смотрит вью `sl_questions_public` — те же вопросы **без**
   `correct_index` и **без** `explain` (по объяснению нередко виден ответ).
3. Проверка ответа — функция `sl_answer()` с `security definer`.

## Почему `?done=` не переедет в тело запроса

У `sl_progress` разрешены `select` и `insert` своей строки, но **`update`
не разрешён вообще**. Уровень поднимает только `sl_finish_test()`: она сама
считает верные ответы по закрытой таблице, сама знает порог (4 из 6 обычный
уровень, 6 из 8 — дәуір сынағы на каждом двадцатом) и сама решает, открылся
уровень или нет. Клиент присылает только пары «вопрос — выбранный вариант».

Единственное, что ребёнок меняет сам, — выбранная ветка (`sl_set_track`),
и это безопасно: прогресс при смене не теряется по устройству механики.

## Как залить

```bash
# 1. Схема
#    Supabase → SQL Editor → New query → вставить schema.sql → Run

# 2. Контент из прототипа
python3 export.py > seed.sql
#    → вставить seed.sql в SQL Editor → Run

# 3. Проверка (в том же редакторе)
select count(*) from sl_questions;   -- 240
select count(*) from sl_heroes;      -- 80
select set_no, count(*) from sl_questions group by 1 having count(*) <> 6;
--   ^ должно вернуть 0 строк
```

И главная проверка, ради которой всё делалось:

```sql
set role authenticated;
select * from sl_questions limit 1;         -- 0 строк
select * from sl_questions_public limit 1;  -- 1 строка
reset role;

select column_name from information_schema.columns
 where table_name = 'sl_questions_public';  -- correct_index здесь быть НЕ должно
```

## `export.py` — почему парсер, а не ручной перенос

Контент правится в прототипе: там его видно на экране и проверяет `?test=1`.
База — производная. Как только перенос делается руками, две копии расходятся
в первый же день.

Скрипт **падает, а не молчит**, если контент не сходится: не шесть вопросов
в наборе, повтор имени героя, повтор текста вопроса, описание вне 300–650
знаков, ветки разной длины. Лучше не залить ничего, чем залить брак.

На первом же запуске он поймал то, чего не видел прототип: три объяснения
короче пятнадцати знаков (`«63 ÷ 9 = 7.»` — показывает счёт, но не называет
правило). Семь самых слабых объяснений переписаны.

## Что ещё не сделано

- **Клиент ещё не переключён на сервер.** Прототип продолжает работать
  на `localStorage`; переключение — вторник по плану, и его надо делать
  вместе с реальным Supabase-проектом, а не вслепую.
- **Диагностика (`../nish/`) тоже считает результат на клиенте.**
  Для неё это менее критично (нет прогресса, который выгодно накрутить),
  но поле `kind` в `sl_questions` уже готово: `base` — школьная программа,
  `nish` — формат НИШ, диагностика берёт по одному вопросу каждого вида.
- **Фото 1000 ағаш** — отдельная задача: Supabase Storage + политика,
  по которой фото ребёнка видно ему и куратору до модерации.
