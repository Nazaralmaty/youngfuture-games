## 0. Что уже есть и на чём это всё строится

- **Sort Arena** (`sort_arena.html`) — пилот арены. Механика: Water-Sort/Colony-Flow — корзины
  (ұя) с яйцами (жұмыртқа), тап переносит верхнюю группу одного вида, свободных корзин 1–2.
  17 тапсырм = один биом (Балапан). Учебный слой — эквивалентность чисел (5–6 класс), доля
  «слепого» режима (без цветовой подсказки) растёт по кривой от 8-й тапсырмы.
- **Math Arcade** (`math_arcade.html`) — более старая аркада, тоже на бридже.
- **Бридж** `studyline-bridge.js` — контракт игра↔приложение: `SL.init/ready/progress/finish/close`.
  Игра не считает XP, шлёт сырой результат. Работает через `postMessage`/нативный мост, если игра
  реально встроена в приложение (`SL.isInApp === true`).
- **Гейм-дизайн уровней ребёнка** — `StudyLine_ГЕЙМИФИКАЦИЯ_ДЕҢГЕЙ_RU.md`: 30 уровней / 6 рангов
  (Балапан → Бүркіт), «Логика аренасы» — это карта 100 узлов = 6 биомов × ~17 узлов, разблокируется
  по рангам. Sort Arena — первый биом, пилот на одном предмете (математика).
- **Правило из ревью Sort Arena, которое нельзя повторить:** первая версия была тривиальной
  сортировкой «положи красное к красному» — решается без раздумий, это не игра. Переписана на
  механику с настоящим тактическим ограничением (мало свободного места → тупик при ошибке).
  **Любая новая механика ниже обязана иметь такое же настоящее ограничение**, иначе это чек-лист,
  а не тайм-киллер.

## 1. Задача 1 — вторая арена: жаратылыстану, механика Flow Connect

### 1.1 Почему не ещё один Water Sort

Sort Arena уже занял нишу «стек с ограниченным местом». Повторение той же механики под другим
предметом — это перекраска, не вторая игра, и ощущается как одно и то же. Нужен **другой жанр**
с тем же уровнем «залипательности» и тем же принципом: реальное планирование, не чек-лист.

**Выбор: Flow Connect** (жанр Flow Free / Infinity Loop / Zip — один из самых воспроизводимых
хитов hyper-casual последних 10 лет, наравне с Water Sort). Ядро: на сетке разбросаны пары
одноцветных точек, нужно соединить каждую пару непрерывной линией **без пересечений**, линии
вместе должны заполнить **все** клетки поля. Одно неверное соединение перекрывает единственный
путь для другой пары — это то самое настоящее ограничение, тот же принцип, что и в Sort Arena,
но выражен другим способом (пространство путей, а не стек).

### 1.2 Предмет и тема

**Жаратылыстану, 5–6 класс** (это уже названо следующим предметом после математики в задаче
Элжана). Пары для соединения — не абстрактные цвета, а **пары по смыслу**:

- процесс → результат (`суда еру` → `ерітінді`)
- организм → класс (`қоян` → `сүтқоректілер`, `қарлығаш` → `құстар`)
- агрегатный күй → пример (`қатты күй` → `мұз`)
- себеп → салдар (`Күн қызады` → `су буланады`, водный цикл)
- табиғат құбылысы → анықтама

Материал берётся из школьной программы жаратылыстану 5–6 сынып (природные явления, агрегатные
состояния, круговорот воды, классификация живых организмов, простые причинно-следственные цепи).
Контент-команда даёт финальный список пар — **правило то же, что в Sort Arena: контент — данные,
не код** (один JS-массив пар, генератор строит из него уровни, не наоборот).

### 1.3 Кривая обучения — применяем урок из ревью Sort Arena сразу, не через итерацию

Sort Arena сначала держала «настоящий счёт» только на уровнях 15–17, ревью это поправило —
доля вслепую должна расти с 8-го уровня, а не с 15-го. **В новой игре делаем правильно с первого
дня**, не повторяя ошибку:

| Тапсырма | Режим | Что тренирует |
|---|---|---|
| 1–6 | **түс** — просто цветные точки, без текста | Освоение правила: линия не пересекается, поле заполняется целиком |
| 7–14 | **ұғым** — на точках подписи пары, цвет пока подсказывает | Экспозиция: ребёнок видит пару и физически соединяет её, закрепление термина |
| 8→15 | доля точек без цветовой подсказки растёт по кривой (как в Sort Arena после правки: ~25% на 8, ~50% на 11–12, 100% на 15–17) | Начиная с середины блока экспозиции уже нужно читать и понимать пару, а не только вести линию по цвету |
| 15–17 | **ұғым вслепую** — только подписи, ноль цвета | Обязательное понимание смысла пары, чтобы понять, какие две точки вообще соединяются |

Сложность по осям: число пар (3→7), размер сетки (5×5→7×7), доля вслепую (см. выше), плотность
пересекающихся путей (сетка становится теснее — меньше «свободного воздуха» между линиями).

### 1.4 Разбор ошибок и недельная шкала — переиспользуем готовое решение, не изобретаем заново

Sort Arena уже решила два вопроса, которые всплывут и здесь один в один:

- **Экран «Қателермен жұмыс» каждые 5 тапсырм**, вопросы по темам, где ребёнок ошибся именно в
  этой сессии, антиугадайка (800 мс до принятия тапа, 1000 мс пауза после промаха, варианты
  перемешаны, отвлекающие — правдоподобные, не случайные). Переносится как есть, меняется только
  банк вопросов (жаратылыстану вместо арифметики).
- **Недельная шкала вместо стрика** — уже реализована в Sort Arena, копируется без изменений.
  Стрик запрещён продуктовым документом `StudyLine_ГЕЙМИФИКАЦИЯ_ДЕҢГЕЙ_RU.md` («наказывает за
  пропуск») — это не мнение разработчика, это уже принятое решение.

### 1.5 Генерация уровней — другой алгоритм, не DFS-солвер от Sort Arena

Важно не копировать солвер Sort Arena бездумно — задачи разной природы:

- Sort Arena проверяет решаемость **готовой** случайной раскладки перебором (DFS с памятью) —
  подходит, потому что раскладок мало комбинаторно.
- Flow-паззлы **гарантированно решаемы**, если генерировать от решения назад — стандартный приём
  жанра: сначала процедурно вырастить непересекающиеся «змейки», которые вместе покрывают всю
  сетку (случайное блуждание с бэктрекингом при тупике), затем стереть тело линий и оставить
  только пары конечных точек как задачу игроку. Уникальность решения не гарантируется тем же
  способом, что и в Water Sort (это не всегда обязательно для казуальных паззлов, но проверить
  тестом всё равно нужно — см. ниже).
- Сид фиксируется номером тапсырмы — тот же принцип, что в Sort Arena («переиграть» = та же
  задача, не новая случайная).

**Обязательный тест-файл** (`nature_flow.test.js`, без фреймворка, `node ...`, по образцу
`sort_arena.test.js`):
- все 17 раскладок решаемы **этим же алгоритмом восстановления линий**, независимая проверка —
  не «генератор пометил как решаемый», а фактическая проверка, что линии не пересекаются и
  покрывают все клетки;
- раскладка детерминирована по сиду;
- каждая пара терминов/подписей действительно соответствует правильному ответу — сверка со
  списком контента, а не с тем, что сгенерировал сам генератор (та же дисциплина, что в
  `sort_arena.test.js` для проверки 225 выражений).

### 1.6 Визуал, джус, маскот

Правила Sort Arena, раздел 2 («Джус, а не правила, держит тайм-киллеры») переносятся без
изменений: приземление/соединение линии — не «исчез/появился», а анимация протяжки линии с
лёгким pulse на замыкании пары, вспышка частиц цвета точки, комбо-полоска, питч звука ползёт
вверх на серии подряд. Никакого таймера, никакого штрафа, бесплатная отмена хода.

Маскот — процедурный скелет по образцу `src/soz_sogysy/render.js` (`Bone`/`Skeleton`, позы через
`pose()`), как и в плане Sort Arena. **Не тот же птенец Балапан** — тот привязан к общей лестнице
рангов ребёнка (30 уровней/6 рангов), а не к предмету. Для жаратылыстану подходит небольшое
лесное/природное существо (например ёжик или лисёнок) — 2–3 позы (idle/happy/sad), без единого
внешнего файла, тот же довод про хостинг, что и в Sort Arena.

Палитра — та же база StudyLine (`--violet #6d4bff`, `--cyan #21d4fd`, `--lime #9be870`,
`--gold #ffce4a`), плюс собственный акцент биома (зелень/охра под тему природы), чтобы игра
считывалась как «из той же семьи», но не была визуальным клоном Sort Arena.

### 1.7 Техническая обвязка — без изменений от конвенции

- Один файл `studyline/games/nature_flow.html`, canvas для сцены, DOM для HUD, `touch-action:none`.
- `SL.init({game:'nature_flow'})` / `SL.ready()` / `SL.progress({level, stars, moves, par, ...})` /
  `SL.finish({score, correct, mistakes, durationSec})` — тот же контракт, что у Sort Arena.
- `level` уже есть в `game_sessions` (миграция сделана для Sort Arena) — новых полей в схеме для
  этой игры не нужно, `game` уже текстовое и принимает любой слаг.
- Мобильный контейнер `max-width:460px; height:100svh; max-height:920px`.

## 2. Задача 2 — Flappy English → арена StudyLine

### 2.1 Что есть сейчас и почему это НЕ арена

`games/flappy-mr1nbd272vmh0.html` — рабочая, проверенная механика: птица летит, в стене — два
проёма с переводом слова, нужно влететь в проём с **правильным** переводом. Просто и залипательно,
переиспользовать стоит как есть. Но по контракту это **другой продукт**, не StudyLine:

- вообще не подключена к `studyline-bridge.js` — нет `SL.init/finish`, прогресс никуда не уходит;
- это лид-магнит для взрослой аудитории 1English: CTA в конце — «Напиши СТАРТ на номер», словарь
  `WORDS[]` — офисная лексика для взрослых (`working`, `calling`, `meeting`, `typing`) — не
  соответствует детской программе StudyLine (5–6 класс);
- лежит в `games/` (конвенция самостоятельных аркад с `games-db.js`), а не в `studyline/games/`
  (конвенция игр внутри арены на бридже).

Это не баг, это два разных продукта с общим куском кода — движок игры одинаково хорош для обоих,
переносить нужно **логику полёта и звук**, не файл целиком.

### 2.2 Что меняется

1. **Новый файл** `studyline/games/flappy_english.html` — самостоятельная копия, не правка
   лид-магнита в `games/`. Тот остаётся как есть для 1English-воронки, трогать его не нужно.
2. **Убрать**: экран регистрации/CTA «СТАРТ на номер», WhatsApp-номер, всё про 1English.
3. **Добавить бридж** — тот же контракт, что у Sort Arena:
   ```
   SL.init({ game:'flappy_english' });
   SL.ready();
   SL.progress({ level:n, stars, correct, mistakes });   // на каждый проём/раунд
   SL.finish({ score, correct, mistakes, durationSec, difficulty });
   ```
4. **Словарь — под учебную программу StudyLine, не офисную**. Готового банка слов для 5–6 класса
   в репозитории нет (проверено — есть только офисный список у Flappy и в `books.js` для читалки,
   это другой материал). Контент-команда даёт список слов уровня 5–6 класса; структура данных
   остаётся той же (`{en, kk, e}` — английское слово, казахский перевод, опционально пример).
   Разбить банк по тапсырмам вместо трёх фиксированных сложностей (easy/medium/hard) — **уровень
   арены = набор слов растущей сложности**, не ручной выбор игроком, тот же принцип прогрессии,
   что у Sort Arena («Оңай/Орташа/Қиын» становится этапами карты, а не стартовым меню).
5. **17 тапсырм = 1 биом**, тот же формат, что у Sort Arena и планируемой nature_flow:
   - 1–6: короткие частотные слова, два явно разных по смыслу отвлекающих варианта;
   - 7–14: слова длиннее, отвлекающий вариант — правдоподобная ошибка (похожее слово, не
     случайное) — тот же принцип анти-угадайки, что и в разборе ошибок Sort Arena;
   - 15–17: словосочетания или слова в контексте примера — не всегда очевидна ассоциация;
   - каждые 5 тапсырм — экран повторения слов, где ребёнок ошибся в сессии (тот же паттерн
     «Қателермен жұмыс», банк — не темы математики, а именно те слова, на которых он промахнулся).
6. **Звук и мотор полёта — переиспользовать без переписывания.** Процедурный Web Audio движок
   в исходнике уже в духе правила репозитория (ноль внешних файлов) — берём как есть, это готовая
   работающая часть, не нужно делать заново.
7. **Карта/вход** — такой же узел арены, открывается через тот же карточный экран пути, что и
   остальные предметные арены (см. план «100 узлов» в `StudyLine_геймификация_заметки_RU.md`).

### 2.3 Явно НЕ делать в этой задаче

## 3. Задача 3 — база данных

### 3.0 Находка: базы для арены **нет вообще**, и не потому, что Элжан не там искал

Пройдено по коду. Вывод: в репозитории живут **две параллельные системы**, и ни Sort Arena, ни
Math Arcade **не пишут ни строки** ни в одну настоящую базу за пределами `localStorage` браузера.

| | `games/*.html` (Flappy, Ninja, Whack, Word...) | `studyline/games/*.html` (Sort Arena, Math Arcade) |
|---|---|---|
| Подключено | `db/games-db.js` | `studyline-bridge.js` |
| Куда пишет | Реальный Supabase-проект (`ckayydaqncvnbecjlltf`, ключ в самом файле `games-db.js`), таблицы `players`/`game_sessions` из `db/schema.sql` | `postMessage` наружу — приложению, которое его слушает. Работает, **только если игру реально открыли внутри нативного приложения StudyLine** |
| Что происходит в браузере напрямую | Пишет в Supabase по-настоящему, есть экран входа по телефону | `SL.isInApp` = false → сообщения просто печатаются в `console.log`, никуда не сохраняются. Прогресс внутри уровня живёт только в `localStorage` (`sl_sort_arena_v1` и т.п.) |

**Именно поэтому «игра помнит меня», но новых таблиц не видно**: то, что выглядит как память —
это `localStorage` самого браузера на конкретном устройстве (переустановил браузер/зашёл с
другого телефона — прогресс пропадёт). В Supabase для Sort Arena/Math Arcade **не создано и не
дописано ни одной строки**, потому что код, который бы это делал, туда никогда не звал: бридж
рассчитан на нативное приложение StudyLine, а нативного приложения ещё не существует
(в vault есть только HTML-концепты кабинета, не рабочее приложение) — `studyline/test/simulator.html`
подтверждает это прямо: это лог сообщений моста в интерфейсе, а не настоящий бэкенд, он ничего
не сохраняет.

### 3.1 Решение — не выдумывать третью систему, соединить две существующие

`games-db.js` уже делает ровно то, что нужно: вход по номеру телефона без email/SMS, таблицы под
эту же модель данных (`players`, `game_sessions` с `game`, `level`, `score`, `correct`, `mistakes`,
`max_combo`, `duration_sec`, `source`), недельный лидерборд, RLS. Это не черновик — это рабочий,
уже подключённый к реальному Supabase-проекту код. Просто Sort Arena и Math Arcade его никогда
не звали.

**Правило подключения — оба пути одновременно, не «или-или»:**

```
если SL.isInApp === true:
    как сейчас — SL.progress()/SL.finish() уходят в приложение,
    оно само решает, как и куда сохранять (когда появится нативный бэкенд)
если SL.isInApp === false (тестовый прогон в браузере — то, что происходит сейчас у Элжана):
    дополнительно писать напрямую в Supabase через games-db.js:
    DB.init({ game }) → DB.mountAuth() (экран входа по телефону, уже готов) →
    в конце партии DB.finish({ score, correct, mistakes, maxCombo, durationSec, difficulty })
```

Логика: пока нативного приложения нет, единственный способ реально проверить пилот на детях —
через браузер, а раз через браузер, значит нужна прямая запись в Supabase. Когда приложение
появится, оно возьмёт на себя сохранение через бридж, а прямая запись останется резервным путём
для тестов вне приложения — переключатель уже есть (`SL.isInApp`), просто сейчас у него нет
второй ветки.

### 3.2 Что сделать в схеме

**Шаг 0 — проверить, применена ли `db/schema.sql` вообще.** Открыть Supabase → Table Editor →
проверить, есть ли `players` и `game_sessions`. Если нет — прогнать файл целиком через SQL Editor
(он написан безопасным для повторного запуска, судя по `if not exists`/`drop policy if exists`
по всему файлу). Если есть, но пустые — это подтверждает находку из 3.0: таблицы существуют,
просто в них ничего не пишут.

**Шаг 1 — добавить `topic_mastery`.** Черновик уже есть в `SORT_ARENA_РЕВЬЮ_RU.md`, раздел 3.2,
это не новая идея, а доведение уже принятого решения до миграции:

```sql
create table if not exists public.topic_mastery (
  player_id       uuid references public.players on delete cascade,
  topic           text not null,          -- 'fractions','percent','powers','division',
                                           -- 'nature_water_cycle','nature_states', 'vocab_en_5_1' и т.д.
  correct_streak  int not null default 0,
  error_count     int not null default 0,
  last_attempt_at timestamptz,
  next_review_at  timestamptz,            -- SM-2-lite: 1д → 3д → 7д → 14д
  primary key (player_id, topic)
);

alter table public.topic_mastery enable row level security;

drop policy if exists topic_mastery_own on public.topic_mastery;
create policy topic_mastery_own on public.topic_mastery
  for all using (auth.uid() = player_id) with check (auth.uid() = player_id);
```

`topic` — общее поле для всех трёх предметных арен (математика, жаратылыстану, английский), одна
таблица на все игры, а не по таблице на игру — ровно то, о чём предупреждало ревью: mastery
кросс-игровой, ему не место внутри файла одной игры.

Пишется из `SL.progress({type:'drill', topic, correct})` — этот вызов **уже есть** в
`sort_arena.html` (строки 1948/1954), просто раньше ему было некуда падать за пределами
приложения. `nature_flow.html` и `flappy_english.html` шлют события в том же формате.

**Шаг 2 — прогресс по карте отдельная таблица не нужна.** `game_sessions.level` (миграция уже
сделана для Sort Arena, раздел 7 схемы) плюс индекс `(player_id, game, level desc)` уже отвечают
на вопрос «какой максимальный узел пройден по игре X» — считается агрегатом, заводить отдельную
таблицу под то же самое было бы дублированием источника истины.

**Шаг 3 — `source` в `game_sessions` уже различает `web`/`studyline`** — писать `web`, когда
запись идёт из standalone-прогона через `games-db.js` (раздел 3.1), это уже предусмотрено схемой,
менять не нужно.

### 3.3 Что НЕ делать

- Не заводить отдельный Supabase-проект под предметные арены — используем тот же
  `ckayydaqncvnbecjlltf`, что и у остальных игр репозитория, одна база на все игры.
- Не переносить бридж на прямую запись в Supabase внутри приложения — когда появится нативный
  StudyLine, у него будет свой бэкенд с полноценной проверкой хода (см. `SORT_ARENA_РЕВЬЮ_RU.md`,
  п. 3.1, «сервер не доверяет клиенту») — прямая запись из standalone-браузера это временный мост
  для пилота, не финальная архитектура.
