# Sort Arena — ревью учебного слоя и дорожная карта

> Ревью от 2026-08-02. Презентация (короткая версия): опубликована как Claude Artifact — ссылка у Элжана в чате.
> Контекст: [SORT_ARENA_ТЗ_RU.md](SORT_ARENA_ТЗ_RU.md) — игра собрана, статус «дать ребёнку и смотреть».
> Триггер ревью: обсуждалась идея gate-механики «после каждых 5 уровней — жди сутки либо сдай тест, чтобы продолжить сразу». Разобрано советом (/council, 4 роли: security, performance, simplicity, devil's advocate) + дополнено отдельно с учётом того, что игра будет встроена в приложение с полноценной базой/бэкендом (не самодостаточный HTML без сервера).

---

## 1. Итог совета: почему time-gate — не тот рычаг

Все четыре роли сошлись на одном: **wait-24h-or-test gate решает удержание, а не обучение**, и создаёт больше проблем, чем решает.

- **Противоречит ТЗ.** Раздел 2 п.5 ТЗ прямо требует «никакого таймера и штрафа». 24-часовая блокировка — штраф с отложенным действием, тот же механизм страха, перенесённый из уровня в мета-слой. Это паттерн energy-систем free-to-play мобилок (Candy Crush lives), а не edtech — ни Duolingo (hearts — про ошибки внутри урока, не про блокировку прогресса во времени), ни Khan Academy (доступ открывается через demonstrated mastery, без искусственных задержек) не используют «жди сутки» как механизм.
- **Малая выборка на пилоте.** При 17 уровнях gate сработает 2–3 раза за весь пилот — статистически ничтожно, чтобы понять, работает ли механика вообще.
- **Три исхода, ни один не даёт данных об обучении.** Ребёнок либо ждёт (теряет вовлечение), либо угадывает тест до правильного ответа (если тест без защиты от угадывания — это капча, не проверка знаний), либо закрывает игру и не возвращается.
- **Настоящая проблема — не частота проверки, а сам core loop.** 14 из 17 уровней (82%) не требуют реального счёта: цвет яйца дублирует ответ, ребёнок может пройти визуально, вообще не считая выражение. Только 15–17 (принудительный blind-режим) заставляют считать. Gate — заплатка поверх loop, который сам не тренирует навык.
- **Технически gate на клиенте не защитить.** Если прогресс/таймер в `localStorage` (как сейчас прогресс игры, ключ `sl_sort_arena_v1`), обход — смена системных часов, `localStorage.removeItem(...)` в консоли, или просто открыть игру в приватном окне. Честный gate требует серверной метки времени — но теперь бэкенд будет, так что это решаемо (см. раздел 3).

**Рекомендация совета:** убрать wait/test-gate. Вместо неё — обязательный «разбор ошибок» из 2–3 задач по темам, где ребёнок реально ошибся в этой сессии, каждые 5 уровней. Это часть прогрессии, не барьер снаружи: следующий уровень открывается после разбора, но обходного пути «подождать и получить так же» просто нет, потому что нет пути, которым можно срезать нечестно.

## 2. Throughput-разбор core loop (performance-роль)

| Блок | Режим | Реальный счёт |
|---|---|---|
| 1–6 | түс (цвет) | ≈0% — чистая моторика |
| 7–14 | сан с цветом | цвет подсказывает, можно не считать |
| 15–17 | сан вслепую | обязателен |

За типичную сессию реальная математическая работа сосредоточена в последних 3–5 минутах игры — throughput обучения на большей части сессии близок к нулю, хотя выглядит как math-контент.

**Дешёвое исправление:** сдвинуть blind-режим раньше — не с 15-го уровня, а начиная с 8–10-го гасить цветовую подсказку на части яиц. Соотношение уже вынесено в одно поле `blind` в `levelCfg()` (ТЗ п.7.2) — менять безопасно, инфраструктура готова.

## 3. Что меняется с полноценным бэкендом

Игра будет частью приложения с базой — значит три вещи, которые на голом HTML-файле нельзя было сделать честно, теперь можно и нужно:

### 3.1 Сервер пересчитывает результат, не доверяет клиенту
Сейчас `SL.finish(result)` (`studyline-bridge.js:224`) отправляет сырой JSON одним payload — score, correct, mistakes, durationSec. Ничто не мешает подменить объект в консоли перед отправкой. Комментарий в самом мосте уже фиксирует правильный принцип: *«игра НЕ считает XP, она отправляет сырой результат, XP начисляет бэкенд по своим правилам»* — тот же подход нужно распространить на сам факт прохождения уровня/теста: игра шлёт **лог ходов** (какая корзина → какая корзина, таймстамп), бэкенд сам пересчитывает, легален ли результат. Это же закрывает дыру для «теста, чтобы продолжить» — иначе ребёнок может просто отправить в консоли фиктивный «прошёл тест».

### 3.2 Mastery/прогресс по темам — не в игре, а в приложении
Дроби, проценты, степени встречаются не только в Sort Arena — если spaced repetition посчитать внутри одного HTML-файла игры, это не будет работать для других игр StudyLine (карта 100 узлов, кланы и т.д. используют общий прогресс ребёнка). У моста уже есть `SL.progress(data)` (`studyline-bridge.js:207`) — предназначен ровно для промежуточных событий. Правильная архитектура:

- игра при каждой ошибке/успехе шлёт `SL.progress({topic: 'fractions', correct: false, expression: '½·8'})`;
- центральный бэкенд StudyLine (не таблицы этого репо) ведёт таблицу вида:

```sql
create table topic_mastery (
  player_id    uuid references players,
  topic        text,           -- 'fractions', 'percent', 'powers', 'division', ...
  correct_streak int default 0,
  error_count    int default 0,
  last_attempt_at timestamptz,
  next_review_at  timestamptz, -- SM-2-lite: 1д → 3д → 7д → 14д
  primary key (player_id, topic)
);
```
- решение «разблокировать / повторить эту тему» принимает бэкенд, а не HTML-файл конкретной игры. Это единственный способ, чтобы адаптация работала кросс-игрово.

### 3.3 Уровни можно генерировать, а не только хардкодить
После обучающего блока 1–6 (правило игры, без учебной нагрузки) — пул выражений с весом по слабым темам ребёнка вместо фиксированных 17 раскладок. Раскладку по-прежнему нужно прогонять через существующий солвер (DFS с памятью, уже в игре) перед показом — принцип «нерешаемый уровень = сломанная игра» не меняется.

### 3.4 Миграция `level` в `game_sessions`
Уже зафиксировано в ТЗ п.7.3 как открытый пункт: *«пока номер тапсырмы уходит только в `details` через `SL.progress`»*. Без колонки `level int check (level between 1 and 100)` в `game_sessions` серверу нечем считать прогрессию/gate/mastery — это блокер для всего раздела 3, стоит сделать первым.

### 3.5 Родительская аналитика — почти бесплатный побочный продукт
Тепловая карта слабых тем ребёнка — это агрегация `error_count` из `topic_mastery` по темам, ничего нового считать не нужно. Это то, что реально продаётся школам в B2B-заходе (см. `Продажа технологии (B2B)/`), в отличие от самого факта наличия gate.

## 4. Приоритеты (impact / effort)

| # | Что | Impact | Effort | Зачем |
|---|---|---|---|---|
| 1 | Сдвинуть blind-режим на уровни 8–10 | высокий | низкий | Одно поле в `levelCfg`, инфраструктура уже есть |
| 2 | Убрать time-gate → обязательный разбор ошибок каждые 5 уровней | высокий | низкий | Снимает противоречие с ТЗ, обхода нет по построению |
| 3 | Streak-бонус (звезда за игру подряд по дням) вместо блокировки | средний | низкий | Та же цель — ежедневный возврат — без риска фрустрации |
| 4 | Миграция `level` в `game_sessions` | средний | низкий | Блокер для gate/mastery на сервере — сделать первым из бэкенд-пунктов |
| 5 | Сервер пересчитывает результат из лога ходов | высокий | средний | Закрывает подмену результата с клиента, нужно и для B2B-отчётности |
| 6 | Topic-mastery на `SL.progress()` в центральном бэкенде | высокий | средний | Один раз для всех игр StudyLine, реальный spaced repetition |
| 7 | Родительская тепловая карта слабых тем | средний | низкий | Побочный продукт mastery-таблицы, продаётся школам |
| 8 | Процедурная генерация уровней после 1–6 | средний | средний | Снимает потолок в 17 задач, ждёт данных с пилота |

**Что НЕ делать сейчас:** полноценный adaptive-difficulty engine, доп. биомы (2–6), отдельный UI родительского кабинета — это инфраструктура для контент-платформы, которой ещё нет. Simplicity-роль совета: сначала данные с реального ребёнка на существующих 17 уровнях (это уже в ТЗ п.7.1), потом масштабирование.

## 4б. Сделано по этому ревью (2026-08-02)

Пункты 1–4 закрыты в коде. 5–8 — половина на центральном бэкенде StudyLine, из игры сделана только её сторона контракта.

### ✅ #1 — blind сдвинут на 8-й уровень, и он теперь доля, а не выключатель
Было: `blind: true/false`, реальный счёт только на 15–17 (25% яиц). Стало: `blind` — доля от 0 до 1, растущая по кривой 8→0.25, 10→0.4, 11–12→0.5, 13–14→0.75, 15–17→1.

**Реальный счёт вырос с 25% до 60% яиц** (цифра печатается тестом). Бесцветное яйцо нельзя положить наугад — надо посчитать и его, и то, на что кладёшь.

Доля берётся **у каждого значения отдельно**, а не в среднем по полю: при случайном броске могло выйти, что у одного числа бесцветны все четыре яйца, а у другого ни одного. Рядом с бесцветными всегда остаются цветные яйца-опоры, по которым видно соответствие «цвет ↔ число» — это то, что делает подъём плавным, а не обрывом.

### ✅ #2 — time-gate не делался; вместо него разбор ошибок
Time-gate в игре не было и не появился. Добавлен экран **«Қателермен жұмыс»** каждые 5 тапсырм.

- Вопросы строятся **только по темам, где ребёнок реально ошибся** в этой сессии, чаще ошибался — раньше в очереди.
- Ошибка фиксируется там, где она настоящая: попытка положить яйцо на неподходящее в учебном режиме — это и есть неверный счёт. Тема снимается с обоих яиц (что нёс и на что клал).
- **Ошибок не было — разбора нет.** Наказывать не за что.
- Обойти нечем: пути «подождать и получить то же самое» не существует.

Защита от угадывания (открытый вопрос №1 из раздела 5 — закрыт):
- варианты не принимают тап первые **800 мс**;
- после промаха — пауза **1000 мс**, вариант гаснет, но правильный **не подсвечивается**;
- варианты перемешаны, отвлекающие — правдоподобные промахи (соседние значения, удвоил, поделил пополам), а не случайные числа.

Проверено в браузере: ранний тап по правильному ответу не засчитывается; три верных ответа закрывают экран и пускают на следующий уровень.

### ✅ #3 — недельная шкала вместо streak
Здесь **сознательное расхождение с ревью**. Ревью предлагает «звезда за игру подряд по дням», но `StudyLine_ГЕЙМИФИКАЦИЯ_ДЕҢГЕЙ_RU.md` прямо запрещает стрики: *«Стрик наказывает за пропуск и после срыва выталкивает ребёнка из продукта совсем»*, и предписывает недельную шкалу.

Сделана недельная шкала: семь точек на карте, сегодняшняя в кольце, день отмечается **по факту решённой тапсырмы**, а не по открытию игры. Обнуляется в понедельник сама. Пропуск дня ничего не отнимает — цель (ежедневный возврат) достигнута, риск фрустрации снят. `daysThisWeek` уходит в `SL.finish`, чтобы бэкенд мог начислить бонус по своим правилам.

### ✅ #4 — миграция `level` в `game_sessions`
`db/schema.sql`, раздел 7: колонка `level int` (nullable — у аркад без карты узла нет), проверка диапазона 1–100, частичный индекс `(player_id, game, level desc)` для «максимальный пройденный узел». Скрипт по-прежнему безопасно перезапускать.

### ◐ #5, #6 — сторона игры готова, сервер за командой
Игра теперь шлёт в `SL.progress` не только итог, но и **сырьё для независимого пересчёта**: стартовую раскладку, полный лог ходов (`{from, to, k}`) и список ошибок с темами. Сервер может проверить легальность каждого хода своим солвером и не верить присланному «я прошёл».

Каждое выражение помечено темой (`add`, `sub`, `mul`, `div`, `frac`, `percent`, `pow`) — это то, из чего бэкенд собирает `topic_mastery`. Ответы в разборе тоже уходят событиями `{type:'drill', topic, correct}`.

Чего в игре сознательно **нет**: самого `topic_mastery` и spaced repetition. Как и сказано в ревью, это кросс-игровой прогресс, ему не место внутри одного HTML-файла.

#7 (родительская карта тем) и #8 (процедурная генерация) — по ревью ждут данных с пилота. Биомы 2–6 — тоже.

## 5. Открытые вопросы к решению

- Anti-guessing защита для «разбора ошибок»: минимальное время до принятия тапа, перемешанные варианты, запрет мгновенного повтора — иначе это капча, а не проверка знаний.
- Где именно живёт `topic_mastery` — в схеме этого репо (`db/schema.sql`) или в основном бэкенде приложения StudyLine (вероятнее, раз прогресс кросс-игровой)?
- Нужно ли вообще «тест, чтобы продолжить сразу» как опция, или полностью заменить на обязательный разбор ошибок без альтернативы ожидания?
